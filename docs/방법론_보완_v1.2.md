## M-01 · 6.7 정제 규칙 검토·승인 (신설)

### 목적

자동 검사(6.6)는 "무엇이 틀렸는가"만 알려 준다. "어떻게 고칠 것인가"는 데이터 엔지니어가 혼자 정하지 않는다.
보정·격리·비움은 원장의 숫자를 바꾸고, 그 숫자는 KPI·추적·추론(S7)·AI 답변(S9)에 그대로 쓰이기 때문이다.
S3에서는 **이슈마다 검토 자료를 만들어 현업과 함께 처리 방식을 정하고**, 결정과 근거를 승인 기록에 남긴다.

### 시점

1. S3 첫 적재(publish)가 대사를 통과한 뒤 — 정제 규칙의 초안(S1 품질 이슈 '상' + S3 FK 검사에서 새로 발견한 것)이 적용된 상태
2. S3 승인 전. 결정이 바뀌면 규칙을 고치고 다시 적재·대사한 뒤 승인한다

### 참여자

| 역할 | 맡는 일 |
|---|---|
| 데이터 엔지니어 | 검토 자료 작성, 원천 조회, 결정 반영(규칙 수정·재적재·대사) |
| 도메인(PI) 컨설턴트 | 업무 의미 해석, 권장안 판단, KPI 영향 검토 |
| 현업 담당자(생산·품질·기준정보 등 데이터 소유 부서) | 실제 사실 확인(입력 오류인지, 공용 계정인지 등), 처리 방식 결정, 원천 정정 수용 |

### 검토 자료 구성 (이슈 1건당 1장)

이슈를 **하나씩 순서대로** 보여 주고, 결정을 받은 뒤 다음으로 넘어간다. 한 장에 아래 5가지를 담는다.

| 순서 | 내용 | 작성 요령 |
|---|---|---|
| ① 원천 데이터 | 문제 행과 같은 맥락의 행(같은 LOT의 전후 공정, 같은 품목의 다른 등록 등) | 원천 컬럼 이름 그대로. 문제 값은 굵게 표시 |
| ② 교차 확인 | 다른 테이블·다른 기록과 비교한 결과 | "다른 LOT 77건 중 76건은 검사 시각 = 완공 시각"처럼 **전체 분포와 비교**한다 |
| ③ 분석 | 원인 추정과 영향(어떤 KPI·추적·계산이 틀어지는가) | 사실과 추정을 구분해 쓴다 |
| ④ 처리 방식 선택지 | A/B(/C) — 방식마다 내용과 영향 | 현재 적용된 방식과 권장안을 표시한다. 권장안이 없으면 비워 둔다 |
| ⑤ 재현 쿼리 | 현업·검토자가 직접 돌려 볼 수 있는 조회 문 | 한 줄 명령으로, 원천 스테이징(stg) 기준 |

### 처리 방식의 종류

| 방식 | 언제 쓰나 | 원장에 미치는 영향 |
|---|---|---|
| 중복 정리(dedupe) | 같은 대상이 표기만 달리 여러 번 등록 | 1행만 남김 |
| 격리(quarantine) | 값 자체를 믿을 수 없고, 바로잡을 근거도 없음 | 행을 적재하지 않음 |
| 참조만 비움(nullify_orphan) | 행은 맞지만 참조 대상이 없음 | 해당 참조 컬럼만 NULL |
| 다른 값으로 대체(replace_orphan) | 같은 업무의 다른 기록에서 올바른 참조를 찾을 수 있음 | 참조 컬럼을 근거 값으로 바꿈 |
| 보정(correct) | **서로 독립된 근거 2개 이상이 같은 값을 가리킬 때만** | 값을 고침. 보정 컬럼은 합계 대사에서 뺌 |
| 표시(flag) | 판단을 미루고 현업 확인만 요청 | 그대로 적재 |

원칙:
- 모든 처리는 원래 행을 `audit.quarantine`에 행 전체로 남긴다. 원천은 바꾸지 않는다.
- 보정·대체는 "그럴듯한 값"이 아니라 **원천 안의 다른 기록**에서 가져온다. 근거를 규칙의 note에 적는다.
- 같은 원인의 이슈가 여러 테이블에 퍼져 있으면(예: 생산실적·완공·생산실적 설비) 한 번에 같은 방식으로 결정한다.
- 원장에서 고친 것과 별도로 **원천 정정 요청**(입력 오류 행 삭제, 공용 계정 사용 금지 등)을 결정 목록에 함께 적는다.

### S2로 되돌아가는 결정

S3에서 매핑 명세 자체를 바꿔야 하는 경우가 생긴다(예: 표준 필수 속성을 원천이 채우지 못함).
이것도 같은 방식으로 검토 자료를 만들어 현업과 정한다. 정한 뒤에는:

1. S2 계획·명세를 고치고 `automap run`·`check`로 다시 생성한다(자동 근사 대응이 새로 생기지 않았는지 확인)
2. S2 승인 기록의 "사후 변경"에 남긴다(M-02)
3. S3를 다시 적재·대사한다

### 결과물

| 결과물 | 내용 |
|---|---|
| 정제 규칙(`s3_plan.yaml` rules) | 방식·조건·근거(note)·결정일 |
| S3 승인 기록 | 이슈별 원천 확인 결과 · 결정 · 영향 행 수 · 원천 정정 요청 · 서명 |
| `audit.quarantine` | 처리 전 원래 행(원천 정정 요청의 근거) |

### 적용 예시 (IMPIX, 2026-10-30)

| 규칙 | 이슈 | 원천 확인으로 알게 된 것 | 결정 |
|---|---|---|---|
| R01 | 품목코드 중복 | 표기만 다른 같은 품목 | 중복 정리 |
| R02 | BOM 자품목 미등록 | 입력 오류 | 격리 + ERP BOM 행 삭제 요청 |
| R03·R04·R09 | 없는 생산오더 번호 | 같은 오더 번호가 3개 테이블에 퍼짐 | 참조만 비움(한 번에 결정) |
| R05 | 파라미터 값 규격 10배 초과 | 상한의 150~570배 — 센서·단위 오류 의심, 바로잡을 근거 없음 | 격리 |
| R06 | 착공 작업자 미등록 | 포장 단말 공용 계정 OP01 | 완공 작업자로 대체 |
| R07 | 양품+불량 ≠ 투입 | 다음 공정 투입·공정검사 양품과 비교해 +3 과다 입력 확인 | 보정(근거 2개 일치) |
| R08 | 완공 < 착공 | 검사 시각 = 완공 시각(77건 중 76건), 다음 공정 착공 시각 | 보정(근거 2개 일치) |
| R10 | 회사 등록자 SYS | 시스템 계정 | 참조만 비움 |
| S2 회귀 | 본사 조직의 공장 없음 | 두 공장을 함께 관리하는 본부·팀 | 본사(HQ) 공장 추가 |

초안(첫 적재)과 비교하면, 표시(flag)로 두었던 R07·R08은 원천 검토로 근거를 찾아 보정이 되었고,
"작업자 미등록"으로 보았던 R06은 공용 계정이라는 사실이 확인되어 대체로 바뀌었다.
**원천을 현업과 함께 보지 않았다면 틀린 해석으로 규칙이 확정되었을 사례**다.

## M-02 · 5.8 승인 — 사후 변경

승인된 명세가 하위 단계(S3 이후)에서 바뀌면 승인 기록에 "사후 변경" 절을 두고
변경 내용·이유·결정한 단계·결정일을 남긴다. 명세 상태는 approved를 유지하되, 변경된 명세는 다시 검토자 확인을 받는다.

## M-03 · 부록 A 체크리스트 (S3 추가 항목)

- [ ] 정제 규칙마다 검토 자료(원천·교차 확인·분석·선택지·재현 쿼리)를 만들었다
- [ ] 이슈마다 현업과 처리 방식을 정했고, 보정·대체는 원천 안의 근거가 있다
- [ ] 원천 정정 요청 목록을 데이터 소유 부서에 전달했다
- [ ] S2 회귀 결정은 S2 명세·승인 기록(사후 변경)에 반영하고 다시 적재·대사했다
